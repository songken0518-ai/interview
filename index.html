面試格式摘要

鏈加科技有限公司，面試官 Ella。約好 9/24（四），提供 10:00-12:00 / 14:00-16:00 / 16:00-18:00 三個時段（尚未收到公司確認是哪一段，注意看信箱或訊息）。線上面試，約 2 小時，含一個 coding 測試，明確允許使用自備習慣的 AI coder 輔助。測試範圍是 backend + LLM API 相關，加上 agent 設計原理及問題討論——代表除了寫得出來，對方會花時間跟你聊「為什麼這樣設計」，這份題庫的重點也放在這裡。

Backend 基礎與 API 設計題

這一區考的是你寫完一支 API 後，對方會逐項碰的基本功力。

  1. 為什麼選 FastAPI（而不是 Flask/Django）？ 期待答案提到原生 async、Pydantic 整合的輸入驗證、自動產 OpenAPI 文件。
  2. 路由設計：POST /agent/handle 這種 endpoint，請求驗證失敗時回什麼？ 預期要談到 422（Pydantic 自動拋）跟 400（自己發的業務邏輯錯誤）的區別，不能全部回 500。
  3. 同步、async def，還是改成背景任務（BackgroundTasks）？ 關鍵在於呼叫 LLM API 是 I/O bound，用 async 不會 block 住其他請求，但如果內部還在用同步的 openai SDK 呼叫就還是會 block，要能談到這個隱藏陷阱。
  4. 輸入驗證用 Pydantic model 還是手寫 if 判斷？ 期待答案是模型定義型別、必填、範圍，錯誤訊息結構化，比手寫判斷更一致、更容易維持。
  5. 錯誤處理策略：會不會把 exception 直接回傳給前端？ 不應該把 stack trace 或內部錯誤細節直接暴露給使用者，應該用統一的錯誤格式（例如 {"error": {"code":..., "message":...}}）包起來，內部細節寫進 log。
  6. 狀態碼怎麼分？ 200 成功、400 請求參數錯、401/403 權限、404 找不到資源、429 太多請求、500 未預期錯誤——要能舉例每一種在你的 API 裡對應什麼情境。
  7. API 版本管理、向後相容怎麼處理？ 常見答案是 URL 帶版本號（/v1/...）或用 header，新增欄位用 optional、不隨便改既有欄位型別。
  8. 測試怎麼寫？ 這裡會連到你工具鏈已經用過的手法——用假的 client（fake response）取代真正打 API，不打網路也能測到邏輯分支；問你會不會 mock 外部依賴、怎麼測邊界情況（空輸入、超長輸入、格式錯誤）。
  9. 如果這支 API 未來要撐更大流量，你會先改哪裡？ 常見方向：加 cache、把慢的 LLM 呼叫改非同步排隊、加 rate limit、拆分讀寫。不用背答案，重點是你能講出取捨（例如 cache 換來的是資料新鮮度風險）。

LLM API 串接與穩健性題

這區直接呼應信中「backend + LLM API」，也是你自己 C 題型（LLM API 穩健化）練過最相關的一塊。

  1. 429 錯誤有幾種，處理方式一樣嗎？ 關鍵是區分 insufficient_quota（額度用完，重試也沒用，應該立刻失敗並通知）與其他 429（rate limit，符合時間重試會成功），兩種不能用同一套邏輯處理。
  2. 重試策略怎麼設計？ 預期談到指數退避（exponential backoff）加抖動（jitter，避免大量請求同時重試造成 thundering herd）、設上限次數、要知道自己關掉 SDK 內建的 max_retries（否則自己的重試邏輯跟 SDK 內建的會疊在一起，實際重試次數比預期多，或者延遲時間不可控）。
  3. 這支 API 逾時了，前端要看到什麼？ 不會永遠卡住，要設合理的 timeout，逾時回結構化錯誤（不是直接 500），並讓使用者知道可以重試。
  4. Streaming 回應中途失敗怎麼處理？ 要能講出 event: error 這類錯誤事件、已經送出去的部分怎麼處理（是保留還是告訴使用者失敗重來）。
  5. 成本控制：一個請求會消耗多少額度，怎麼防止失控？ 你自己工具鏈裡 agent.py 用 MAX_ROUNDS=8、MAX_REPEATS=2 這套一定會被問到——要能講出為什麼需要上限（防止使用者亂輸入讓 agent 一直空轉、浪費額度）。
  6. 模型選擇的取捨？ 例如 gpt-4o-mini 與更大模型的速度/成本/品質取捨，你自己的 auto_intake.py 裡有實測記錄（同題 gpt-4o-mini 漏接 agent 迴圈、gpt-5-mini 質量好但慢很多），這個對比也能講。
  7. 如何讓測試不碰真正的 API？ 需要講出依賴注入（你的 handle_agent(..., client=None) 設計 client 可以從外部傳進來），測試時推假的 client 進去，不打網路、不花額度。
  8. 還會問：量化上限、比如對接額度、Usage tier、Org spend limit 這些防呼癘機制你知不知道，可以簡單提到 OpenAI 平台本身就有 org-level spend limit 可以設。

Tool-calling / Agent 設計原理題

依據實際面試講座與 2026 年跡與資料整理，這一區最常被問到的兩種深度：

基礎層：

  1. 講一遍 ReAct 迴圈（Thought → Action → Observation）怎麼變成具體的程式邏輯？ 你自己的 agent.py 就是這個邏輯的實作，要能與一句具體描述：每一輪模型決定要不要呼叫工具、呼叫完把真實結果回餵給模型、重複直到模型決定可以回答。
  2. 工具白名單為什麼必要？ 不能讓模型自己決定要執行什麼函式（絕對不能用 getattr/eval 去動態呼叫），所有可用工具是事先定好的 registry/dict，模型只能從這個點名集裡選。這是安全設計題，不是性能考量。
  3. 工具呼叫失敗怎麼處理？ 不會直接讓程式 crash，而是把錯誤包成結構化訊息（例如 {"error": "..."}）回餵給模型，讓模型自己決定下一步（重試、換工具、或告訴使用者做不到）。
  4. tool_call_id 對應為什麼重要？ 多個工具同時被呼叫時，回覆必須正確對回原始的 tool_call_id，不然模型會混淆哪個結果屬於哪個呼叫。

進階/可能被追問的層次：

  1. 怎麼防止 agent 無限迴圈？ 這是最常被問、也是你工具鏈實際實作過的問題。完整答案應包含：步數上限（你的 MAX_ROUNDS=8）、同參數重複呼叫次數上限（你的 MAX_REPEATS=2，避免模型用同樣參數一直重試同一個工具）、無進展偵測（state hash 連續 N 次不變就強制停止），以及絕對時間上限。「交給模型自己判斷何時停」不是合格答案。
  2. 多輪對話中的狀態怎麼管理？ context window 有限，不能把所有歷史訊息一直堆進去，要考慮記憶摘要、只保留相關的 tool result。
  3. 如何評估一個非確定性（non-deterministic）的 agent 好不好？ 這題對曾經實作過評估流程的人比較有利，常見方向是 golden dataset 加 LLM-as-judge 對照 rubric 評分，比對人工標籤。
  4. 只能看到最終結果、看不到 agent 中間踏過哪些步驟時，怎麼 debug？ 這對應可觀測性（observability）：每一輪呼叫都要有 trace/log，你的 agent.py 回傳 steps 陣列就是這種設計。
  5. 什麼時候該讓 agent 行動，什麼時候該先反問使用者？ 你自己的練習題就有這個情境（使用者說「我想退款」但沒給訂單編號時，應該反問而不是亂猜call工具），核心是工具需要的必要參數缺失時就該先問人。

Agent 進階討論與情境判斷題

這一區沒有標準答案，面試官要看的是你的權衡思考。

  1. 如果使用者一直問同樣的問題，你的 agent 會一直重複呼叫同一個工具嗎？該怎麼改？ 對應你工具鏈裡的 MAX_REPEATS 設計，可以延伸談到偵測參數重複呼叫次數不只是步數上限。
  2. 工具回傳的資料與使用者實際想問的不一致時（例如查到資料但格式不對），該讓模型自己推斷還是直接失敗？ 權衡點在於自動化方便與錯誤風險。
  3. 假設使用者在對話中試圖讓 agent 做超出權限的事（例如「幫我直接改別人的訂單」），你的設計怎麼擋？ 這對應工具層的權限驗證，不能單靠提示詞去防。
  4. 這個 agent 未來要接更多工具（僅存 3 個變 20 個），現在的設計會不會撞掛？ 談到工具描述會塞滿 context、模型選錯工具的機率會上升，可能需要先用小模型/規則篩選相關工具再交給主模型再次決策。
  5. 如何判斷一個問題適合用 agent，還是簡單的規則引擎就夠了？ 這題在考你會不會為了用 AI 而用 AI，合理答案是流程固定、決策樹能解決就不需要 LLM。
  6. 如果這個 agent 需要跨多個子任務分工（multi-agent），你會怎麼分工？ 可以談到 orchestrator/worker 模式，或先談單 agent 將任務拆成多次呼叫就夠用，不一定需要真的拆成多個 agent。

針對你自己程式碼的追問模擬

這區不是通用題庫，是直接對應你實際會交出去的東西——先自己在心裡想過一遍怎麼答。

  1. 為什麼 MAX_ROUNDS 設 8，不是 5 或 20？ 要能講出你的取捨邏輯（太小會造成複雜任務提早被截斷，太大浪費額度與時間），就算這個數字是估的也要說得出合理的判斷基準。
  2. 為什麼不用 getattr 或 eval 來動態呼叫工具，而是寫死一個 REGISTRY dict？ 這是安全設計題，答案要指向：避免模型被誘導呼叫任意 Python 函式、防止任意程式執行風險。
  3. 為什麼 handle_agent 要提供 client=None 這個可覆寫的參數，而不直接在函式裡建 OpenAI client？ 這是依賴注入的基本思考，目的是讓測試能推假的 client 進去、不直接打真實 API。
  4. 你用 Pydantic 驗證 LLM 回傳的 JSON，驗證失敗時怎麼處理？ 對應你 auto_intake.py 裡 _ask_json 的設計：把錯誤訊息回餵給模型要它重新輸出，限制最大重試次數，超過就真的失敗，不會無限重試。
  5. 金鑰遮蔽那套邏輯為什麼要先做、才送去給 LLM 分析？ 安全設計題，答案是不能信任任何送進 LLM 的內容不會外洩，要在送出前就攔下來。
  6. 如果現場面試官直接要你現場改掉 MAX_ROUNDS、或加一個新工具，你會怎麼改？ 這是實作題，需要你真的看得懂自己交出去的碼才改得到，所以一定要自己讀過一遍 Cowork 產出的程式碼。

你可以反問面試官的問題

在 agent 設計討論段落結束前反問 1、2 題，既能顯出你有實戰思考，也能當作你自己判斷這份工作適不適合。

  • 「你們實際產品裡的 agent，目前最大的穩健性問題是什麼？是工具呼叫失敗、還是模型判斷錯誤？」

  • 「你們目前會不會用 LLM-as-judge 這類方式評估 agent 品質，還是主要靠人工抽檢？」

  • 「這個團隊對於 AI coder 輔助產出的程式碼，code review 的標準會不會跟人寫的不一樣？」

面試前 15 分鐘衝刺重點

時間不夠就只看這一段。

  1. 背一次「防止 agent 無限迴圈」的完整答案：步數上限 + 同參數重複上限 + 無進展偵測 + 時間上限，並能用你 agent.py 的 MAX_ROUNDS/MAX_REPEATS 具體舉例。
  2. 背一次 429 的兩種區別（insufficient_quota vs rate limit）跟重試要進 backoff + jitter。
  3. 背一次「為什麼不用 getattr/eval 動態呼叫工具」的安全理由。
  4. 準備好前一則對話結果裡的一句公式回答（「這段是 AI coder 輔助寫的，但參數/設計是我自己定的——因為...，我有...驗證過」），談任何碼都套得上。
  5. 自己重要：公司已經明確說可以用 AI coder，不用擔心用 Cowork 會被視為作弊，但參數/設計是我自己定的——因為...，我有...驗證過套得上。
