1.1 這個專案在解什麼問題

AR 眼鏡的近眼顯示模組（微顯示面板 + 波導光學）在出廠前必須校正三類成像缺陷：

缺陷物理來源使用者感受本專案怎麼量
亮度與色彩不均 cos⁴ 自然漸暈、波導出瞳擴展效率的波長相依性、面板發光效率變異 邊緣變暗而且偏色 min/max 均勻度、std/mean、CIE 1976 Δu′v′
幾何畸變 + 橫向色差 透鏡／波導的徑向畸變；折射率隨波長變化 直線變彎、邊緣出現彩邊 殘餘位移的 RMS/max（px 與 arcmin）、逐通道位置差
雙眼對齊誤差 左右光機的組裝公差 眼疲勞、頭痛，嚴重時複視 同一內容在左右眼成像位置的垂直／水平差（arcmin）

最關鍵的一個判斷：不能事後修圖

相機的影像處理可以事後修復拍到的照片。近眼顯示器不行——使用者的眼睛直接看光學系統的 輸出，我們唯一能改的是「送進面板的訊號」。

所以整條校正鏈只能是預補償（pre-compensation）：把缺陷的逆運算預先施加在內容上， 讓它通過光學系統之後正好變成我們要的樣子。

驗證也必須對應地閉迴路：校正後的面板訊號要再過一次成像模型，量的是眼睛真正看到的 結果。若只是把量測影像 warp 回去算 PSNR，數字會很漂亮但沒有物理意義——那張修好的影像沒有 任何途徑進到使用者眼裡。

1.3 三個核心決定

決定一：gain map 必須定義在面板座標，而且幾何要先做

光度不均有兩個來源：面板側（發光效率變異，定義在面板座標）與光學側（漸暈，定義在觀測座標）， 中間隔著一個幾何畸變。看起來要分兩張圖處理，但其實可以精確合併。設 u = F(x) 為前向幾何映射：

O(F(x)) = P(x) · T_pan(x) · T_opt(F(x)) = P(x) · [ T_pan(x) · T_opt(F(x)) ]

中括號裡是一張純面板座標的圖。也就是說不論漸暈發生在光路的哪一段，從面板端看都等價於 單一張面板座標的增益圖。這個推導直接決定了三件事：

  1. 只需要估一張 gain map，不必分離兩個來源（它們本來就不可分離）
  2. gain map 必須定義在面板座標，不是量測座標
  3. 因此幾何校正必須先於光度校正——把平場量測搬回面板座標唯一的方法就是用已校正的 幾何模型做反投影

決定二：預補償只需要正向模型

O(F(x)) = P(x)　　⟹　　要 O = T 就必須　P(x) = T(F(x))

也就是「把目標影像在 F(x) 處取樣」。預補償方向天然不需要求逆，而校正端擬合出來的 （由「面板已知點位 → 觀測到的點位」對應）正好就是正向模型 F。兩邊剛好接上。

加上光度後完整的套用順序是：

P(x) = T(F(x)) · g(x)　　　先幾何預畸變，再在面板座標乘增益

反過來做（先乘增益再預畸變）會把增益圖也一起扭曲，錯得很隱晦、不會拋錯。 tests/test_corrector.py::test_apply_correction_order_is_prewarp_then_gain 把它釘死。

決定三：刻意保留模型失配（避免 inverse crime）

如果模擬端與校正端用同一組模型，殘餘畸變會掉到 1e-12 px，數字漂亮但只證明了解方程能力。 本專案刻意讓兩端不對稱：

模擬端（真值）校正端（擬合）
徑向係數k1, k2, k3k1, k2
切向係數p1, p2p1, p2
畸變中心偏心 (+6.5, −4.0) px固定在影像中心
光度不均帶限隨機場（正弦疊加，非多項式）+ cos⁴ + 梯度高斯平滑後的逐像素圖
量測PSF + Poisson + 讀出雜訊 + 8-bit 量化—

因此殘餘畸變是 0.058 px 而不是 1e-12 px。 test_residual_distortion_is_not_suspiciously_perfect 會在殘差小於 1e-4 px 時 讓測試失敗——寧可測試紅燈也不要一個假的完美數字。

2.1 線性光與 gamma——為什麼所有運算都在線性光域

「像素值 128」不代表「亮度是 255 的一半」。顯示器有一條 EOTF（電光轉換函數）， 典型是 亮度 ∝ 驅動值^2.2。所以驅動值 128/255 ≈ 0.5 對應的亮度只有 0.52.2 ≈ 0.22，也就是兩成二而不是一半。

這件事為什麼致命。 光度校正要做的是「把發光量乘上增益 g」。如果你直接把驅動值 乘上 g，實際的發光量會變成 g2.2 倍——而且因為 g 隨位置變化，這個誤差也隨位置變化， 校正之後均勻度會比校正前更差。這正是本專案實機路徑實際踩過的坑：均勻度從 66% 掉到 59%。

本專案的約定：所有內部運算一律在線性光域（值域 [0,1] 正比於亮度）。 gamma 編碼只出現在兩個地方：

  • 輸出給人眼看的 PNG（fileio.to_display_uint8）
  • 送進真實螢幕之前（rig.show_and_capture 負責編碼，螢幕的 EOTF 再還原回線性光）

另一個推論：影像重取樣必須在線性光域做。在 gamma 域做雙線性內插，等於對非線性量取平均， 邊緣會產生可見的亮度偏差。

2.2 影像重取樣與「映射方向」——最容易搞錯的一件事

OpenCV 的 cv2.remap(src, map, ...) 是這樣運作的：

對每一個輸出像素 u，到 map[u] 指定的輸入位置去取樣
　　dst(u) = src( map[u] )

也就是說 map 是「輸出 → 輸入」的方向，跟直覺相反。這導致同一個幾何模型 F， 在兩個不同用途要用相反方向的映射表：

用途輸出格點是需要的 map本專案的函式
模擬成像
O(u) = P(F⁻¹(u))		觀測影像F⁻¹（觀測→面板） GeometryModel.inverse_map()
預補償
P(x) = T(F(x))		面板影像F（面板→觀測） GeometryModel.forward_map()
一個乾淨的結論：預補償方向天然只需要正向模型 F，不需要求逆；而校正端由 「面板已知點位 → 觀測到的點位」擬合出來的正好就是 F。兩邊剛好接上， 整條校正鏈唯一需要求逆的地方只有模擬器。

optics.remap() 把邊界外一律填 0。這是刻意的——它讓「面板未覆蓋的區域」 在後續一路上保持為 0，覆蓋率遮罩可以直接由此推導，不需要另外維護邊界資訊。

2.3 Brown-Conrady 畸變模型

鏡頭畸變的標準參數化。把座標對中心正規化後（v = (x − c)/r_norm， r² = |v|²）：

徑向：　v′ = v · (1 + k₁r² + k₂r⁴ + k₃r⁶)
切向：　tx = 2p₁vxvy + p₂(r² + 2vx²)
　　　　ty = p₁(r² + 2vy²) + 2p₂vxvy
輸出：　x′ = c + r_norm · (v′ + t)
參數意義本專案的量級
k₁ < 0桶狀畸變：離軸點往中心靠模擬 −0.140、webcam −0.185
k₁ > 0枕狀畸變：離軸點往外推—
k₂, k₃高階徑向修正0.035 / −0.012
p₁, p₂切向（鏡片不平行造成）4.5e-4 / −3e-4
cx, cy畸變中心真值偏心 (+6.5, −4.0) px

為什麼用半對角線正規化？ 讓 r 在畫面角落約等於 1，k 係數就與解析度無關， 同一組參數可以套用到不同解析度的面板。

逆運算沒有封閉解

給定畸變後的位置求原始位置，要用不動點迭代（與 OpenCV undistortPoints 同一套路）：

v ← (e − tangential(v)) / radial(|v|²)

對 |k₁| < 0.3 的量級，十餘次即收斂到 < 1e-6 px。本專案預設迭代 20 次， test_optics.py::test_forward_inverse_roundtrip 驗證往返誤差 < 1e-6 px （實測 6e-12 px）。

2.4 單應變換（homography）

兩個平面之間的投影對應，用 3×3 矩陣在齊次座標下表示：

[u′ v′ w]ᵀ = H · [x y 1]ᵀ　　然後　u = u′/w,　v = v′/w

8 個自由度（h₃₃ 可正規化為 1）。它能表示平移、旋轉、縮放、剪切與透視—— 也就是相機沒有正對螢幕時的梯形變形。

實機路徑與模擬路徑的作用順序是相反的。
模擬（AR 光學）：面板座標 →[Brown-Conrady]→ →[相似變換]→ 觀測座標， 畸變發生在顯示模組的光學裡，中心在面板座標系。
實機（相機看螢幕）：螢幕座標 →[單應變換 H]→ 理想相機平面 →[Brown-Conrady]→ 相機像素， 鏡頭畸變在透視投影之後才發生，中心在相機座標系（主點）。

順序弄反不會拋錯，只會讓畸變中心落在錯的座標系、擬合系統性偏掉。 test_capture_planar.py::test_distortion_is_applied_after_the_homography 用一個 巧妙的方式把它釘死：螢幕上投影到相機正中心的那一點，不該被徑向畸變推開。

2.5 cos⁴ 自然漸暈定律

離軸角 θ 處的像面照度正比於 cos⁴θ。四個 cos 各有來源（入射角、出射角、距離平方、面積投影）， 這是純幾何效應，任何成像系統都有。等效焦距由水平 FOV 反推：

f = (W/2) / tan(HFOV/2)　　[像素]　　　cos θ = f / √(r² + f²)

本專案讓 R/G/B 使用不同的等效指數（4.00 / 4.25 / 4.75）來模擬波導耦合效率的 波長相依性——藍光通常衰減較快，結果是邊緣偏黃的色不均。這也是 test_simulator.py::test_vignetting_is_stronger_for_blue 驗證的性質。

2.6 色度：為什麼用 Δu′v′ 而不是 RGB 比值

用 R/G、B/G 的比值來報告色偏，數值大小取決於通道定義，跨系統無法比較，也無法對應人眼 可辨識程度。顯示產業一律用 CIE 1976 UCS 的 Δu′v′——近似均勻色空間，Δu′v′ 的大小 與人眼可辨識程度大致成正比。

XYZ = MRec.709 · RGBlinear
u′ = 4X / (X + 15Y + 3Z)　　v′ = 9Y / (X + 15Y + 3Z)
Δu′v′ = √( (u′₁−u′₂)² + (v′₁−v′₂)² )

前提假設：面板原色為 Rec.709/sRGB、白點 D65。真實 AR 波導模組的原色座標與此有差距， 正式量測必須用實測的原色矩陣取代 colorimetry.RGB_TO_XYZ_REC709。 純黑像素的色度未定義，本專案回傳 NaN 而不是填一個假值——呼叫端必須明確處理無效區。

2.7 PSNR 與 SSIM——意義與三個陷阱

PSNR = 10·log₁₀( MAX² / MSE )　　[dB]，越大越好

MSE 是逐像素平方誤差的平均。PSNR 對整體位移極度敏感（差幾個像素就會掉十幾 dB）， 所以它是幾何校正的好指標，但對「模糊」相對不敏感。

SSIM（Wang et al. 2004）比較局部的亮度、對比、結構三項：

SSIM = [ (2μxμy+C₁)(2σxy+C₂) ] / [ (μx²+μy²+C₁)(σx²+σy²+C₂) ]

陷阱一：在線性光域算 PSNR 會低估暗部誤差

兩者都是為感知編碼訊號設計的。本專案在計算前先做 gamma 編碼 （metrics.core._encode）。

陷阱二：全域亮度尺度會被當成失真

校正後因為 headroom 而整體變暗，PSNR 會扣分——但整體亮度是可調的顯示設定（背光/驅動電流）， 不是空間性缺陷。本專案在計算前以最小平方求出並移除全域亮度尺度：

α = Σ(test·ref) / Σ(test·test)　　然後比較 α·test 與 ref

亮度損失另由 K（峰值亮度保留）單獨、明確地報告，兩件事分開講。

陷阱三：SSIM 在「沒有結構」的區域會退化

SSIM 的 structure 項是 σxy/(σxσy)。當參考影像在某個視窗內是 完全平坦的（σx = 0），而量測影像帶有相機雜訊（σy > 0）時， 該項退化成 C₂/(σy²+C₂) 並趨近 0——它反映的是量測雜訊，不是校正品質。

本專案的 AR HUD 場景實測有 81% 的像素亮度低於 0.02、局部變異數恰為 0， 而實拍的相機雜訊 σ ≈ 0.0099。結果：有結構區域 SSIM 0.688、空白區域 0.147、整體 0.310。

處理方式與本專案處理「被裁切的圓點」一致：沒有有效資訊的地方排除， 並把涵蓋率明確報出來（metrics.core.ssim_textured）。 真實照片沒有這個問題，因為自然影像不存在變異數精確為零的區域。

三種圖卡，全部程序化生成，沒有任何外部素材檔：

圓點抗鋸齒：追到底的一段

圓點的次像素質心精度是整條幾何校正鏈的精度上限，而且它的誤差會偽裝成光學殘差被誤讀。 所以這裡追到了盡頭：

clip(R + 0.5 − dist, 0, 1) 線性近似0.0108 px
N×N 子像素取樣，N=8（誤差 O(1/N)）0.0078 px

3.5 calibration/geometry.py 幾何校正

圓點偵測

Otsu 二值化 → 連通元件 → 面積過濾 → 強度加權質心。用強度加權而非二值質心， 是因為抗鋸齒圓緣帶有次像素資訊，二值化會把它丟掉。

「先有雞還是先有蛋」問題

要擬合畸變必須先知道哪個觀測點對應哪個面板點；但要建立對應又需要先知道畸變。 本專案預設畸變下，角落圓點位移約 90 px，遠大於半個點距（約 60 px）， 直接最近鄰配對必錯。

解法是分三段收斂：

  1. 四角對應：以 x+y 與 x−y 的極值取理想格點與偵測結果的四個角。純徑向畸變保序， 且旋轉遠小於 45° 時對應唯一（本專案的組裝公差是 0.3° 量級，餘裕充足）。
  2. k₁ 一維掃描：對 k₁ 掃 41 個候選值，每個都用四角解一個相似變換，取「閘門內配對數最多」 者。只用一個參數就能吃掉絕大部分位移。
  3. 完整擬合 → 重新配對（收緊閘門）→ 再擬合。

配對率低於 95% 直接拋 CalibrationFailure 中斷，不做靜默降級。

刻意的模型簡化

畸變中心固定在影像中心，不參與擬合。理由：它與相似變換的平移高度共線，同時自由會使 問題病態。代價（真值偏心無法被完全吸收）誠實地反映在殘餘畸變上。

3.6 calibration/photometry.py 光度校正

令 Mc(x) 為反投影回面板座標的白平場響應、Wc := Mc(中心)。 要讓全視場呈現與中心相同的白點：

gc(x) · Mc(x) = K · Wc　⟹　gc(x) = K / ρc(x)， 　ρc := Mc/Wc

物理限制 g ≤ 1（面板不能輸出超過 100% 亮度）　⟹　K ≤ min ρ
K 有一個直接的物理意義：校正後保留的峰值亮度比例。 把邊緣拉亮是不可能的，均勻度只能靠把中心壓暗換來——這個代價由 K 明確量化。 只報 uniformity 不報 K 是自欺。

實務上 K 不取嚴格最小值而取低百分位（target_percentile），並設下限 headroom_floor：單一個異常暗點不該決定整片面板的亮度。代價是那些像素會被夾在 g=1 而留下殘餘不均，這由 clipped_fraction 誠實回報（實測 1.00%）。

邊緣處理：反投影時面板最外圈會取樣到「面板成像區的邊界」，該處線性內插已混入邊界外的 0， 造成一圈假的暗邊。_replicate_border() 直接丟掉那一圈並以最近有效值外推—— 不是猜測，是承認該處無有效量測。

3.7 calibration/binocular.py 雙眼對齊

左右眼顯示同一份虛擬內容（假設內容位於無窮遠，理論視差為零）。因此「同一個面板點在左眼成像 位置」與「在右眼成像位置」之間的差值，就是使用者實際承受的雙眼失準量。

為什麼垂直方向要單獨拿出來講。水平偏差會被人眼的水平聚散（vergence）吸收——那本來就是 判斷距離的機制，有相當大的可動範圍。垂直方向沒有對應機制：垂直聚散（dipvergence）範圍極小， 殘餘垂直偏差無法被融像，直接轉成眼疲勞、頭痛，嚴重時複視。所以雙眼對齊的規格幾乎都是被 垂直項卡住的。

★ 容忍門檻 3 arcmin 是推斷值，未經文獻查證。只用於示範指標如何與人因門檻掛鉤， 不應被當成規格。

3.9 metrics/core.py 量化指標

所有指標一律只在「有效覆蓋區侵蝕後」的遮罩內計算。把黑邊算進去會同時扭曲校正前與校正後的 數字，而且是往有利於「校正後」的方向扭——那是自欺。有效區的損失另外用 ActiveArea 明確報告，不藏在均勻度或 PSNR 裡。

可量測性判定

預畸變之後，若圓點的支撐圓盤跨越覆蓋邊界，圓點會被切掉一部分，強度加權質心就會系統性向內偏—— 量到的是裁切而不是畸變。measurable_dot_indices() 用距離變換判定 「圓點中心到邊界的距離 ≥ 半徑 + 餘裕」，不合格的一律排除，且排除數量必須報出 （校正前後套用同一組點，前後對照才成立）。

這個問題實際發生過：圖卡邊界設 0.06 時，最外圈圓點落在可校正區外， 逐通道誤差 R(7.37) > G(5.43) > B(3.20) px，正好對應各通道覆蓋區大小 R < G < B。 修法有兩個層次：圖卡邊界由安全框反推（0.06 → 0.13），以及指標排除不可量測的點。

相機響應曲線：非做不可的一步

webcam 幾乎都在輸出端套了一條近似 gamma 的曲線。不線性化就直接量光度不均， 量到的「均勻度」是曲線的形狀而不是亮度分布。

我們量到的是合成響應 y(v) = g(f(v))，f 是螢幕 EOTF、g 是相機響應，單靠一組 (v,y) 無法分開。 本專案假設螢幕遵循標準 EOTF（gamma 2.2）——顯示器的 EOTF 有標準規範且各家接近， 相機的響應則沒有任何規範可言。於是量到的 (L, y) 就是相機的響應曲線 g，取反函數即可線性化。

非單調時直接中斷並指出「最常見原因是自動曝光沒關掉」，同時把量到的曲線值印出來。

兩個「不會拋錯、只會讓數字難看」的方法學陷阱

陷阱一：指標不能在螢幕解析度上算。螢幕只佔相機畫面 53.4%，1920×1080 的內容在相機上 只被約 975×548 個像素取樣。把拍到的影像重取樣回螢幕解析度再算 PSNR/SSIM 等於在放大， 細線與 zone plate 必然糊掉——量到的是相機的取樣不足，不是校正的品質。 推論：圖卡不該放量測系統解析不了的內容。

順帶：量測網格與 cv2.resize 的幾何約定必須一致（輸出像素中心 i+0.5 對應輸入 (i+0.5)/s）。用 align-corners 的 i/s 會差 0.5/s − 0.5 ≈ 0.24 個量測像素—— 那是一個固定位移，不會被幾何校正吸收、也不會在殘餘畸變上顯現（畸變是在相機座標量的）， 只會讓 SSIM 無聲地掉低。

陷阱二：SSIM 不能在沒有結構的區域上算。見 2.7。

第五部　動手實驗

每個實驗都附「預期看到什麼」與「為什麼」。建議用 config/test.toml（約 15 秒一輪）。

怎麼跑：改完設定後雙擊 START.bat，選 2（快速模式，約 75 秒）。 快速模式寫在 out_quick/ 與 out_capture_quick/， 不會覆蓋你先跑好的正式解析度報告。
注意快速模式讀的是 config/test.toml 與 config/capture_test.toml—— 下面的實驗要改的是那兩份設定檔。

實驗 1：把缺陷關掉，驗證整條鏈

# config/test.toml
[defects]
severity = 0.0

預期：均勻度 min/max ≈ 100%、殘餘畸變 ≈ 0、面板覆蓋率 100%、K ≈ 100%、 PSNR 前後幾乎相同。

為什麼重要：如果 severity=0 時「校正後」比「校正前」差，代表校正鏈本身引入了誤差 （例如重取樣、量化）。這是最基本的健全性檢查， test_simulator.py::test_severity_zero_gives_a_perfect_module 就在測這個。

實驗 2：亮度 vs 均勻度的取捨

[calibration.photometry]
headroom_floor = 0.90     # 原本 0.45

預期：K 從約 74% 上升到 90%，但均勻度 min/max 從 96.8% 掉到大約 80%， gain_clipped_fraction 從 1% 飆到二三十 %。

為什麼：K 是「校正後保留的峰值亮度」。強迫 K ≥ 0.90 意味著很多像素需要的增益 > 1，但面板做不到，只能夾在 1 而留下殘餘不均。這是整個專案最能展示「沒有免費午餐」 的一個實驗，面試很適合現場跑。

實驗 3：讓校正端跟不上真實結構

[defects.photometric.panel]
random_max_cycles = 3.5   # 原本 1.1

預期：校正後的均勻度明顯變差（std/mean 從 0.2% 上升到 1% 以上），gain map 看起來 比真實的不均「模糊」。

為什麼：校正端假設光度不均是低頻的，用 smoothing_sigma_px 高斯平滑抑制雜訊。 把真實不均的頻率拉高之後，平滑會把它一起抹掉，校正就跟不上。接著把 smoothing_sigma_px 從 14 調到 4 再跑一次，會看到均勻度回升——但 gain map 會 出現雜訊紋理。這對取捨的兩端都摸過一次。

實驗 4：把圖卡邊界調小，重現「被裁切的圓點」

[patterns.dot_grid]
margin_frac = 0.06        # 原本 0.13

預期：殘餘畸變 max 從 0.34 px 暴增到 5 px 以上，而 RMS 幾乎不變； 報告的「因不可量測而排除」欄位會從 0 變成 8 個左右。

為什麼：最外圈圓點落在預畸變可校正區外，被覆蓋邊界切掉一部分，質心系統性向內偏。 可量測性判定會把它們排除（所以 RMS 沒壞），但如果把判定關掉，這些點會嚴重灌水。 這個實驗能讓你親眼看到「指標的有效性判定」為什麼必要。

實驗 5：關掉橫向色差，單獨觀察幾何

[defects.geometry]
lca_radial_scale_r = 1.0
lca_radial_scale_g = 1.0
lca_radial_scale_b = 1.0
lca_magnification_r = 1.0
lca_magnification_g = 1.0
lca_magnification_b = 1.0

預期：LCA 指標掉到接近雜訊底線（< 0.05 px），三通道的覆蓋率變成一模一樣， 安全框略微變大。幾何指標基本不變。

為什麼：把耦合的效應拆開單獨觀察，是理解任何多缺陷系統的標準手法。

實驗 6：壓力測試量測雜訊

[measurement]
photons_full_well = 2000.0   # 原本 20000，雜訊變 3.2 倍

預期：重投影 RMS 從 0.027 px 上升到約 0.08 px，殘餘畸變隨之上升； gain map 出現可見的雜訊。frames_to_average 的價值在這裡最明顯。

實驗 7：實機路徑——切換參考座標系

# config/capture.toml
[capture.correction]
reference_transform = "similarity"   # 原本 "homography"

預期：校正後拍回來的畫面變成正矩形（透視被消掉了），視覺衝擊很大； 但有效區與安全框明顯縮水。

為什麼：消除透視需要在螢幕上顯示一個梯形預畸變的內容，梯形之外的區域就浪費掉了。 相機越斜、損失越多。這是另一個「代價」的展示。

第六部　除錯手冊

6.1 錯誤訊息對照表

訊息意義怎麼處理
ConfigError: 缺少設定項 config.x.y設定檔少了一個鍵 訊息會列出該層級現有的鍵，照著補上
CalibrationFailure: 圓點偵測數量不足 偵測到的圓點少於預期的 95% 檢查 min/max_blob_area_px、量測曝光、radius_px
CalibrationFailure: 第 N 輪配對率僅 x% 畸變超出 k₁ 掃描範圍，或旋轉太大使極值點對應失效 放寬 k1_search_min/max；確認旋轉遠小於 45°
ResponseError: 響應曲線不單調 相機自動曝光／自動增益沒關掉 調 capture.camera.exposure；換支援手動曝光的攝影機。 訊息會印出量到的曲線值，可看出哪一級跳掉
RigError: 無法開啟攝影機裝置不存在或被佔用 改 camera.index；關掉其他用相機的程式
白平場影像中找不到任何亮區相機沒拍到螢幕，或曝光過暗 先看 out_capture/images/flat_raw.png
有效區為空螢幕沒完整落在畫面內，或 similarity 模式下相機太斜 調整相機位置；改回 "homography"
MSE 為 0：兩張影像完全相同閉迴路評估出問題（不應發生） 代表 render 沒有真的執行，檢查流程

6.2 診斷的思考順序

  1. 先看重投影誤差（報告的「校正內部診斷」表）。這是擬合是否有效的唯一內部憑據。 若 RMS > 0.2 px，問題出在偵測或擬合，不必往下查。
  2. 再看配對率。100% 以外都代表有點沒配到。
  3. 看殘餘誤差的空間分布（報告的 quiver 圖）。誤差集中在邊緣 → 模型階數不足或圓點被裁切； 均勻分布 → 雜訊主導。
  4. 看逐通道的差異。R > G > B 的模式通常代表覆蓋區大小的差異在作祟。
  5. 對照理論上限。PSNR 距上限很近就代表演算法沒問題，瓶頸在物理。

第七部　擴充指南

7.1 加一種新缺陷

  1. 在 config/default.toml 的 [defects] 下加參數（含註解說明物理依據）
  2. 在 simulator/model.py 的對應建構函式中實作，記得乘上 severity
  3. 在 render() 的正確位置插入——順序就是物理順序
  4. 加測試：severity=0 時該缺陷必須消失
  5. 思考：校正端要不要對應處理？如果不處理，它會變成新的模型失配來源（這也是合理的選擇， 但要在 README 寫明）

7.2 加一個新指標

  1. 在 metrics/core.py 加函式，簽名帶 (reference, test, mask, cfg)
  2. 一定要接受遮罩——所有指標只在有效區內計算
  3. 在 metrics/__init__.py 匯出
  4. 在 pipeline.py 的 metrics 字典加一項
  5. 在 report/builder.py 的 _summary_rows() 加一列
  6. 加測試：在已知答案的合成輸入上必須給出已知的值

7.3 換一個畸變模型

例如改成自由形式的雙變量多項式（處理光柵波導的非旋轉對稱畸變）：

  1. 在 optics.py 新增參數 dataclass 與 forward/inverse
  2. 逆運算若沒有封閉解，沿用不動點迭代的模式；務必加往返測試
  3. GeometryModel 的介面（forward_points / inverse_points / forward_map / inverse_map）保持不變，其他模組就完全不用改
  4. 擬合端：_build_model() 與參數向量的打包/解包要對應調整
這就是為什麼 GeometryModel 的四個方法是整個專案的介面邊界—— 只要這四個方法的語意不變，換模型的影響範圍就被鎖在 optics.py 與 geometry.py 兩個檔案內。
